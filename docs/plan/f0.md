# F0 architecture and feasibility backlog

F0 establishes reviewed evidence before the messaging core is implemented.
The repository contains initial evidence for F0.1–F0.5; it does not complete
F0. The release is called Foundation; F0-F6 label implementation stages.

| Work package | Current status | Deliverable and exit evidence |
| --- | --- | --- |
| F0.1 Architecture decisions | Drafted, review pending | ADR register reviewed, trust/deployment boundaries agreed, owners recorded |
| F0.2 Threat model | Expanded design draft; human review pending | Data flows, attacker capabilities, controls and residual risks reviewed |
| F0.3 Encryption feasibility | Candidate exercised in Node/Chrome; production selection blocked | [Offline exchange and assessment](../security/encryption-feasibility.md); audit, durable storage and human review pending |
| F0.4 Domain and API contracts | Proposed contracts and consistency checks; approval pending | [Identity/schema, authorization, OpenAPI and state graph](../protocols/README.md); A01–A07 review and runtime evidence still required |
| F0.5 Test harness | Real-service fixture baseline; production integration pending | [Two-tenant harness](../../tests/Harness/README.md), forced RLS, pool reuse, outbox replay and process-crash recovery; actual application roles/pooling and remaining reliability cases still required |

## Dependency order

Review the architecture and threat boundaries first. Start encryption feasibility
before fixing wire contracts. Use those decisions to define the real two-tenant
harness; then implement identity, persistence and delivery through F1-F3. Policy
and receipts are enforced throughout development, with dedicated F4 verification.

## Decisions still needed

- OIDC provider, membership model and identity/key verification.
- Encryption protocol/library, licensing, device storage and recovery behavior.
- Exact recipient routing privileges, schema and transaction boundaries.
- Review [delivery transitions](../protocols/delivery.md), revocation and expiry races.
- Idempotency/cursor retention, message limits, quotas and fair scheduling.
- Broker topology, retry/dead-letter policy and recovery objectives.
- Hosting region, operational owners and review sign-off responsibilities.

## Evidence rules

F0.3 uses disposable synthetic clients. Passing checks do not close
[native agent checks](../security/agent-safety.md#pending-native-checks) or approve
architecture/cryptography. Review remaining E01–E06 gates before fixing F0.4 wire
contracts around a library.

Store reproducible commands and results with each work package. The F0.5 fixture uses an explicitly non-owner, non-BYPASSRLS role and a real
one-connection Npgsql pool. No production database role/pool exists yet, so this
is not the required application parity evidence. Reuse these scenarios with the
actual application roles and pooling configuration as F1-F3 implement them. State
explicitly when a result is a proposed target or unexecuted scenario. Repository
build/test/format checks are useful developer gates, not release acceptance.
