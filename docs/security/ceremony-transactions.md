# Device ceremony persistence and transactions

F1.4 migration 004 adds the durable ceremony ledger and internal SQL transaction
primitives. It implements storage transitions for initial enrollment, replacement
and revocation against the [staged contract](../protocols/device-enrollment.md).
This guide owns migration 004's storage and transaction semantics. See the
[verifier guide](enrollment-verifier.md) for proof integration and the
[authority guide](enrollment-authority.md) for
principal mapping and execution roles. The [HTTP guide](enrollment-http.md) owns
adapter configuration and deployment requirements.

## Trust and invocation boundary

The functions are `SECURITY INVOKER`, with pinned search paths and no PUBLIC
execute grant. Application invocation uses the
[migration 005 entry boundary](enrollment-authority.md#postgresql-roles-and-rls).
Do not put a migration credential in Gateway, grant
application roles membership in the owner role, or expose these functions as
bearer-only enrollment.

`ceremony_actor` contains tenant selection, issuer/subject, client ID, exact origin,
configuration ID, scopes, ACR, authentication time and token expiry. These are
**trusted projections**, not tokens or independently authenticated database inputs.
SQL resolves the external subject's current membership, establishes transaction-local
tenant/user/issuer/subject context and checks device.manage,
active tenant/user/membership/postman, an explicit unexpired device-management
grant, enabled RP/origin configuration, allowed ACR and fresh authentication/token
deadlines. It cannot verify that a caller obtained those claims legitimately.
The [validated-principal bridge](enrollment-authority.md#principal-mapping) owns
application construction of this projection. Arbitrary owner SQL remains an
administrator trust boundary.

`ceremony_finish` accepts credential ID, normalized public key, BE/BS and counter
from the trusted verifier bridge, bound to a reserved attempt ID and exact request digest.
It does **not** verify signatures, attestation, UP/UV, client data or curve points.
The isolated verifier bridge verifies the original bytes against the reserved challenge,
RP/origin, handle and exact credential/key, then submits that same projection;
SQL checks the reserved device version. Production HTTP wiring remains
pending. No boolean "verified" flag, placeholder verifier or custom signature
format is used. The SQL layer has no cryptographic verifier dependency. The returned
internal verifier snapshot must never be sent directly to an HTTP client.

## Durable records

| Record | Responsibility |
| --- | --- |
| device_configurations | Explicit RP/origin, allowed ACRs, age limit, enabled flag and version; disabled by default |
| device_management_grants | Separate device-management object authority tied to the owner's postman; finite expiry, version and terminal revocation |
| device_ceremonies | Immutable operation/owner/client/origin/configuration binding, expected lifecycle versions, candidate/target references, stage and deadlines |
| device_challenges | One globally unique 32-byte challenge per stage, issue/expiry/consumption times |
| device_commands | Scoped replay digest/result and durable numbered verification reservation |
| device_ceremony_audit | Minimal ceremony/command references, action, identity version and server time |

All six tables enable and force RLS with an explicit owner policy. The
[authority guide](enrollment-authority.md#postgresql-roles-and-rls) owns the subsequent
executor policies and privileges; owner-policy RLS does not confine arbitrary
administrator SQL. Existing runtime device metadata RLS stays unchanged. No new grants are seeded from
F1.3 postman.read authority. Control rows cannot be deleted/rebound; revoked grants
cannot be reactivated. Configuration and grant changes increment their versions.

A partial unique index permits one unfinished ceremony per tenant/user across
both enrollment and revocation. The same owner may retain multiple terminal
ceremonies and pending/abandoned device records from earlier work. Composite
foreign keys bind candidate, current device, postman and commands to that owner.
Stored raw token or WebAuthn response bytes are absent: the request ledger stores
SHA-256 of the exact supplied command bytes, not the bytes themselves. HTTP JSON,
UTF-8, compression and duplicate-field validation remain adapter work; the storage
primitive only enforces a nonempty body of at most 65,536 bytes.

Challenges and user handles must be freshly generated by the trusted caller using
a cryptographic RNG (the harness uses .NET RandomNumberGenerator). They are not
client-selected inputs. A stage challenge expires two minutes after issuance,
capped by the ceremony's five-minute deadline. There is no refresh operation.
Expiry or stale bound context terminates the ceremony and abandons an unactivated
candidate, without changing an existing active device. Cleanup remains disabled
pending A06; no automatic deletion or retention window is invented.

## Transaction protocol

Each invocation is a database transaction; the caller must commit before reporting
success. Expected denials return a small internal JSON outcome. Unexpected SQL
errors require rollback and must not be exposed as raw exception details. These
results are not the public OpenAPI DTOs; the [HTTP adapter](enrollment-http.md)
owns public projection, transport enforcement and request budgets.

1. `ceremony_begin` resolves current authority, checks the expected identity and
   active-device snapshot, fixes the operation and reserves the candidate UUID.
   It commits the initial challenge, begin replay result and audit together.
   Revocation uses the existing device. An exact begin replay returns its original
   options only while that challenge remains current. An expired unfinished
   ceremony can be terminated during a fresh begin so it cannot block the owner
   indefinitely.
2. `ceremony_reserve` locks and rechecks context, then records one of at most five
   attempts for that stage, its exact request digest, observed device version and
   reservation transaction ID. **Commit this transaction before verification.**
   Verification runs outside locks. The primitive returns an internal snapshot
   of the challenge and required public credential/handle material.
3. `ceremony_finish` consumes a successful verifier projection, or `ceremony_fail`
   records a generic failed outcome. A finish/failure in the reservation's own
   transaction is rejected using PostgreSQL's [top-level transaction ID](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-PG-SNAPSHOT).
   Thus a rolled-back reservation cannot be claimed as durable. An interrupted
   committed reservation retains its slot; exact reservation replay returns
   unavailable instead of issuing another verifier job. Recovery may finish that
   same committed attempt if context and deadlines still hold, or let it expire.

Five failed attempts abandon a ceremony. Concurrent unresolved attempts also
consume the five-slot budget, but do not become failures merely because another
attempt finishes first. A valid fifth attempt can succeed. Failed replays remain
failed after authorization; they cannot become success or consume another slot.
A different digest under the same key conflicts. Another key for a consumed
stage conflicts. Keys are scoped by tenant/user, operation/stage and target or
ceremony ID; client/origin/configuration bindings are checked before replay.

Registration fixes the once-attached credential and issues a candidate challenge.
A first-enrollment candidate assertion activates it. For replacement, candidate
proof instead issues a challenge to the exact old credential; only that proof can
revoke the old device and activate the candidate together. Revocation has its own
challenge/stage and terminal effect. Current-credential operations require the
same configured RP as the old credential; RP migration is not a recovery path.

Successful stage effects include challenge consumption, counter/backup updates,
new challenge or terminal lifecycle change, replay result and audit in one
transaction. Nonzero counters must strictly increase at assertion commit; zero to
zero is allowed. BE must match registration, BS cannot be true when BE is false.
Record-version comparison detects changes since the verification snapshot.
Final activation/replacement/revocation increments the user's identity version
**once** in the same transaction, retaining old device attribution and leaving
messaging unavailable. The [authority guide](enrollment-authority.md#postgresql-roles-and-rls)
owns the identity trigger's execution-role boundary. Existing provisioning
status/version behavior remains intact, and safe-integer exhaustion fails closed.

Intermediate successful replay is available only while its returned challenge
remains current and unexpired. Completed replay returns the original completion
identity version/time plus a fresh, consistent current device lifecycle/owner
version snapshot. Current scope, grant and step-up are still required. Replaying
a successful activation after revocation reports the retained revoked device;
it does not reactivate it or require that historical device to remain active.

## Locks, rollback and evidence

Lock order is tenant, user, membership, postman, grant, configuration, ceremony,
then involved devices in UUID order, challenges in stage order and the command
row. The user row serializes same-owner commands.
The current actor/grant/token/step-up deadline is checked again after device/challenge
and command lock waits, and ceremony/challenge deadlines plus lifecycle versions
are checked before effects. `ceremony_finish` also rechecks authority and stage
deadlines after the credential projection write and after all stage writes, so
uniqueness waits on credentials, public keys or the next challenge cannot bypass
deadline checks. Changes after external proof verification therefore cannot
silently use its old snapshot. These guarantees use PostgreSQL [row locks](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)
held until transaction end. No crypto verification, broker or network call belongs
inside the transaction.

Projection shape/uniqueness failures record a failed attempt without a partial
credential write. Audit or later state-write failures propagate so the entire
stage rolls back, including identity version, device changes, challenge consumption
and success replay. The previously committed attempt survives that rollback.
Deadline denial after a write also rolls back those provisional effects, including
credential attachment. Authority expiry returns `forbidden`; stage expiry returns
`conflict` and expires the ceremony, abandoning its pending candidate. Both retain
the committed reservation without recording a failed proof.

The harness exercises real migration/functions with two owners/tenants, scoped
replay, concurrent begins and attempt reservations, ordered initial/replacement/
revocation paths, stale versions and bindings, counter failures, post-lock expiry,
audit failure rollback and database restart. The
[`ExpiryDuringUniqueWriteRollsBackSuccessAndRetainsCommittedReservation` regression](../../tests/Harness/CeremonyTransactionTests.cs)
covers authority/challenge expiry during credential, public-key and next-challenge
uniqueness waits followed by blocker rollback. All identities and proof projections
are synthetic. This is transaction/storage evidence; it proves neither real OIDC
assurance nor WebAuthn possession, HTTP policy enforcement or browser behavior.
